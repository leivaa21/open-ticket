# M1 — the Show aggregate + reservation write side

**Problem:** open-ticket has an API skeleton but no domain. M1 delivers the write side that makes
the whole project credible: an event-sourced **Show** aggregate whose seat reservations are
correct under concurrency — a seat is **never sold twice**, proven by tests, on an in-memory
event store that mirrors the target production semantics. No read models, no web, no HTTP-under-
load yet; this milestone is about the domain being right.

## Scope

The reservation lifecycle for a single show:

```
             ReserveSeats(showId, seatIds, holderId)          ConfirmPurchase(holdId)
  available ───────────────────────────────────▶ held ──────────────────────────────▶ sold
      ▲                                            │
      └──────── ReleaseHold(holdId) / hold TTL expiry ─────────┘
```

- A **hold** is a time-boxed claim on one or more seats (TTL, e.g. 10 min). While held, those
  seats can't be reserved by anyone else.
- **Confirm** turns a live hold into a sale. **Release** (explicit) or **expiry** returns the
  seats to available.
- Invariant, enforced in the domain: **no seat is ever in two live holds, and a sold seat is
  never re-held or re-sold.**

## Decisions specific to M1

- **D1-01 — The Show aggregate is a fold over its event stream.** `decide(state, command) →
events | DomainError` and `evolve(state, event) → state`, both pure. State is reconstituted by
  folding the stream; commands never mutate, they emit events. Aggregate id = `showId`; stream =
  all events for that show.

- **D1-02 — Events (past tense, facts):** `ShowScheduled` (seat inventory defined),
  `SeatsHeld` (holdId, seatIds, holderId, expiresAt), `HoldReleased` (holdId),
  `HoldExpired` (holdId), `SeatsSold` (holdId, seatIds). Commands (intent):
  `ScheduleShow`, `ReserveSeats`, `ConfirmPurchase`, `ReleaseHold`. Names live in
  `packages/contracts` as zod schemas; the domain works in terms of the inferred types.

- **D1-03 — Time is a port (`Clock`), not `Date.now()`.** Expiry is decided against an injected
  clock so tests are deterministic. Expiry is **lazy**: a `ReserveSeats`/`ConfirmPurchase`
  arriving after a hold's `expiresAt` treats those seats as available/invalid — no background
  timer in M1 (a sweeper that emits `HoldExpired` is a later concern; the fold already treats an
  expired hold as dead).

- **D1-04 — `EventStore` port mirrors EventStoreDB.**
  `readStream(streamId) → { events, revision }` and
  `appendToStream(streamId, expectedRevision, newEvents)` that **throws a typed
  `ConcurrencyError` if the stored revision ≠ expected**. The in-memory adapter implements
  exactly this; a fidelity test asserts the conflict behavior.

- **D1-05 — Optimistic concurrency with bounded retry in the use case.** A use case: read stream
  → `decide` → append at expected revision; on `ConcurrencyError`, re-read and retry up to N
  times, then surface a typed `ConflictError`. This is where the contention story lives and is
  unit-tested by interleaving two commands on the same expected revision.

- **D1-06 — Typed domain errors, no throwing strings.** `SeatUnavailable`, `HoldNotFound`,
  `HoldExpired`, `SeatsAlreadySold`, etc. The interface layer (later) maps them to status codes;
  in M1 they're asserted directly in tests.

- **D1-07 — Deterministic ids injectable (`IdGenerator`).** `holdId` generation is a port so
  tests are reproducible; the adapter wraps `crypto.randomUUID`.

## Sub-PR breakdown

1. **PR — contracts: commands + events** (zod schemas, inferred types, exhaustive discriminated
   unions). Pure types + schema tests.
2. **PR — domain: the Show aggregate** (`decide`/`evolve`, the invariant, typed errors). Pure,
   heavily unit-tested including the never-double-sell property and lazy expiry. No ports yet.
3. **PR — application + in-memory infrastructure:** the `EventStore`/`Clock`/`IdGenerator`
   ports, the in-memory event store (with the expected-revision fidelity test), and the
   `ReserveSeats`/`ConfirmPurchase`/`ReleaseHold` use cases with optimistic-retry — including a
   **concurrency test** that interleaves two reservations racing for the same seat and asserts
   exactly one wins.
4. **PR — thin HTTP surface:** `POST` routes for the commands wired to the use cases, zod-parsed
   at the edge, typed errors mapped to status codes; Fastify `inject` integration tests. (Still
   no read side — `GET` of seat state arrives in M2 as a projection.)

## Verify for real (gate two)

Beyond green unit tests: run the API, `POST` a reserve then a confirm, and hit the same seat
twice concurrently (two `inject`ed requests in parallel) — confirm exactly one succeeds and the
other gets a clean typed conflict, not a double-sell.

## Deferred (not M1)

Read models / projections / `GET` seat map (M2), SSE + web dashboard (M3), real EventStoreDB
adapter + load numbers + a background expiry sweeper (M4), payments (faked behind a port when
confirm needs it).
