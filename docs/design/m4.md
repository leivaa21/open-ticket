# M4 — the projector control panel + the real EventStoreDB adapter

**Problem:** M3 made the system watchable, but only at whatever speed it happens to run — the lag
meter mostly reads zero because an in-memory projector catches up instantly. And the whole
"EventStoreDB-shaped ports" claim is still just a claim: no real store has ever been asked to
honor them. M4 fixes both, and they belong in one milestone because they check each other. The
**control panel** (delay, pause, rebuild) makes eventual consistency something you can _drive_ on
screen. The **real store** proves the ports weren't fiction — and, as it turns out, forces one of
them to become honest. Published load numbers move to **M5**, because numbers measured against an
in-memory store would have to be thrown away the moment the store changed. Measure once, on the
real thing.

## Decisions (leivaa, 2026-07-30)

- **D4-01 — Global positions become opaque, comparable tokens; lag becomes time-based.** This is
  the milestone's load-bearing decision, and the in-memory store is what hid it. Our `EventLog`
  port defines `GlobalPosition` as a **contiguous 0-based counter** where `head` is literally the
  event count. EventStoreDB's `$all` positions are **commit/prepare byte offsets** — monotonic and
  totally ordered, but not contiguous, not counts, and not cheap to convert into "how many events
  behind". A faithful adapter cannot satisfy today's port, and faking a counter inside the adapter
  would be a lie that breaks on restart and on any second instance.
  - **Position** becomes an opaque token that supports only `compare(a, b)` and equality —
    serialized as a string in the read DTOs. Everything that matters keeps working: read-your-writes
    is still `asOf >= commitPosition` (D2-05), just through a comparator instead of `>=` on a number.
  - **Lag** stops being "N events behind" as its primary unit and becomes **`behindMs`** — now minus
    the recorded timestamp of the last applied event, `0` when caught up. It means the same thing to
    every adapter and the same thing to a human ("the projection is 2.4s behind"), and it is what
    production observability actually reports. `behindEvents` survives as an **optional** field,
    populated only by adapters that can supply it for free (the in-memory one can; EventStoreDB
    can't).
  - **Rejected:** keeping the integer counter and having the ESDB adapter maintain its own (breaks
    across restarts and instances — a correctness lie in the one place the project claims rigor);
    reporting `behind` in bytes for ESDB and events in memory (a lag meter whose unit depends on
    configuration is worse than no lag meter).
  - This lands **before** the adapter, as its own behavior-preserving refactor, so the adapter has a
    port it can actually implement.

- **D4-02 — The projector is paced per event, through an awaited hook, and costs nothing when
  off.** The control is a `ProjectorControl` in `queries/application/`, and the projector's handler
  awaits `control.pace()` before applying each event. Per-event (not per-batch) pacing is the
  decision: the existing `Scheduler` seam would delay whole coalesced batches, making lag sawtooth —
  climb, then vanish in one frame. Per-event pacing makes lag **climb and drain visibly**, which is
  the entire point of the panel. `pace()` returns `undefined` synchronously when unpaced so the
  unthrottled hot path takes no extra microtask per event — M5 publishes throughput numbers and the
  control must not tax them. `pause()` withholds resolution; `resume()` releases every waiter;
  disposal releases them too, so a paused projector can still be stopped (a subscription whose
  handler never settles is exactly how this would hang, and that gets a test).

- **D4-03 — Rebuild runs in the background and swaps atomically; reads never go down.** "Read
  models are disposable" is a core CQRS claim, so the panel gets a button that proves it. The naive
  version — clear the store and re-subscribe from zero — would make every seat map 404 mid-rebuild.
  Instead the rebuild projects into a **shadow `ReadModelStore`** from position zero while the live
  one keeps serving, and swaps it in once the shadow reaches the head position captured when the
  rebuild started. Zero read downtime, and the swap is observable on the dashboard. This is also the
  boot path once the store is durable (D4-05): a fresh process rebuilds its read models from the log.

- **D4-04 — Dev controls are off by default and unregistered when off.** They are unauthenticated
  mutating endpoints that can stall the read side; this is a public repo whose demo someone will
  deploy. `DEV_CONTROLS_ENABLED` (default **`false`**) gates route registration entirely — when off
  the routes **do not exist** (404, not 403: don't advertise a disabled control surface). `pnpm dev`
  turns them on explicitly, and `.env.example` documents it with the warning attached. The dashboard
  discovers the panel rather than assuming it: `/dev/stream` sends an initial `event: capabilities`
  frame, so the API stays the single source of truth for what's enabled.

- **D4-05 — The EventStoreDB adapter is real, and both adapters pass one conformance suite.** The
  adapter implements the existing `EventStore` + `EventLog` ports against a real server —
  `appendToStream` with expected revision (`NO_STREAM` → the store's no-stream state), `readStream`,
  `$all` reads, and a `subscribeToAll` catch-up feeding `onCommitted`. The payoff isn't the adapter,
  it's the **port conformance suite**: one shared set of behavioral tests (expected-revision
  conflicts, revision sequencing, `$all` ordering, commit wake-ups) executed against **both** the
  in-memory and the EventStoreDB adapter. That suite is the proof the swap was ever real, and it is
  the artifact worth showing a reader. `EVENT_STORE=memory|eventstoredb` selects at the composition
  root; `memory` stays the default so the repo still runs with zero infrastructure.
  - **Check at implementation time:** EventStoreDB was renamed **KurrentDB**, and the maintained npm
    client moved accordingly. Pin whichever package is current and maintained, and note the rename
    in the README rather than silently depending on a legacy name.

- **D4-06 — Container-backed integration tests run in CI, in a separate suite.** Testcontainers
  starts a real server for the ESDB half of the conformance suite. `pnpm test` stays fast and
  infra-free (unit + in-memory integration); `pnpm test:integration` runs the container suite, and
  CI runs both — a gate that only runs locally is a gate nobody runs. Workspace rule stands: the new
  dependencies get an audit pass and a security-auditor review before merge (new network I/O + a new
  client library is squarely in §6's trigger list).

- **D4-07 — Read-model durability stays deferred, on purpose.** Once the log is durable, a restart
  replays it and the read models come back (D4-03's rebuild path). A persisted read store buys
  faster cold starts and nothing else the showcase needs, and it would add a second piece of
  infrastructure to the quickstart. The port stays in-memory; the decision is recorded so the
  absence reads as a choice.

## Dev control API

All under `/dev/projector`, registered only when `DEV_CONTROLS_ENABLED` (D4-04); bodies parsed with
contracts schemas at the edge, like every other inbound payload.

- `POST /dev/projector/delay` — `{ delayMs: int 0..10000 }`. Bounded on purpose: an unbounded value
  is a self-inflicted denial of service on the read side.
- `POST /dev/projector/pause` · `POST /dev/projector/resume` — idempotent.
- `POST /dev/projector/rebuild` — starts a background rebuild, returns immediately with the target
  position; progress and the swap arrive over `/dev/stream`.
- `/dev/stream` gains `event: capabilities` (initial frame, `{ controls: boolean }`) and
  `event: projector` (`{ paused, delayMs, rebuilding }`) so every open dashboard reflects a control
  change made from another tab. The `lag` frame changes shape per D4-01.

## The load contract stampede must satisfy

M5 publishes open-ticket's numbers, and `stampede` is the instrument. This is the consumer-side
spec written **before** stampede is designed, so the tool is built against a real customer rather
than a guess. These are the runs M5 has to produce:

1. **The stampede** (the namesake run) — N virtual buyers POST a reservation for the **same seat**
   on one show, as hard as they can. The claim under test is not a percentile: **exactly one 201,
   N−1 conflicts, zero double-sells.**
2. **Hot show, many seats** — N buyers spread across one show's seats, all serialized through one
   stream. Claim: successful reservations equal distinct seats held, `sold <= capacity`, and the
   optimistic-retry rate stays bounded.
3. **Read fan-out under write load** — heavy seat-map `GET`s while writes run, the read/write
   asymmetry the whole architecture is justified by. Claim: read p99 holds while writes contend.
4. **Projection lag at peak** — with pacing off, how far behind (`behindMs`) the projection falls at
   the sustained write ceiling. This is the number the M4 control panel exists to make legible.

What that demands of stampede, as a contract:

- **Per-response checks with names** — a check is a predicate over a response, counted pass/fail and
  reported as a row. "Exactly one 201" is a claim about a run, not about a request, so:
- **Custom counters, merged across workers** — user-incremented, aggregated over worker threads at
  run end. Together with checks, this is what makes stampede an assertion tool and not just a
  benchmarker. Merging counters and histograms across workers is the real engineering in it.
- **Thresholds → exit code** — `counters.reserved201 == 1`, `checks.doubleSell.failed == 0`,
  `p99 < 250ms`. A run that violates the invariant must fail CI, not print a red number.
- **Setup / teardown hooks with shared state** — setup creates the show and hands every virtual user
  the same `showId`; teardown does the after-the-fact verification (`GET` the seat map, assert
  exactly one seat sold). The invariant is proven **after** the storm, not only during it.
- **Markdown report** — paste-ready into open-ticket's README: the scenario, the throughput, the
  percentile table, and the checks table. "Prove your numbers" is the tool's whole pitch.
- **Open question for stampede's design, not settled here:** SSE-subscriber fan-out (scenario 5,
  M+ concurrent event-stream readers) needs a streaming, long-lived request mode rather than
  request/response — likely a later stampede milestone, and open-ticket should not block on it.

## Sub-PR breakdown

1. **docs — this design.** Plus the `docs/decisions.md` entries for D4-01 and D4-05.
2. **refactor — honest positions + time-based lag (D4-01).** Contracts DTOs, the `EventLog` port,
   projector, view builders, and the web lag meter. Behavior-preserving for the in-memory adapter;
   the in-memory position type becomes a token that happens to wrap a counter. Tests updated, not
   weakened.
3. **feat(queries) — `ProjectorControl`: pace, pause, resume (D4-02).** Application layer only, no
   HTTP. Tests: pacing delays application without dropping events, pause holds and resume releases
   in order, a paused projector still stops cleanly, and the unpaced path adds no scheduling.
4. **feat(queries) — background rebuild + atomic swap (D4-03).** Shadow store, target position,
   swap. Tests: reads stay served throughout, post-swap state is byte-identical to the live one, a
   rebuild racing live appends converges.
5. **feat(api, web) — control endpoints + dashboard panel (D4-04).** Gated registration, the
   capabilities + projector frames, the panel UI (slider, pause/resume, rebuild) with its
   disabled-state rendering. Tests: routes absent when the flag is off, bounds rejected at the edge,
   panel hidden without capabilities.
6. **feat(infra) — EventStoreDB adapter + port conformance suite (D4-05).** The adapter, the shared
   conformance suite run against both adapters, `EVENT_STORE` selection in config and the
   composition root, `docker-compose.yml` for local runs. The largest PR; split adapter and
   conformance suite if the diff outgrows review.
7. **ci — testcontainers integration job (D4-06),** plus the security-auditor pass on the new
   dependency and network surface.
8. **docs — mark M4 complete:** README quickstart for both store modes, screenshots of the panel
   driving lag, and the `CLAUDE.md` current-state line.

## Verify for real (gate two)

Green tests do not prove this milestone; the milestone is a thing you watch.

- `pnpm dev`, open `/dev`, drag delay to ~2s and click seats: lag climbs steadily, the seat map goes
  visibly stale, then drains smoothly when delay returns to 0 — climbing and draining, not
  sawtoothing.
- Pause, drive ~20 reservations, confirm the feed stalls while writes keep succeeding (the write
  side is unaffected by a dead read side — the CQRS point), then resume and watch it catch up.
- Hit rebuild with a seat map open in another tab: **no 404, no flicker**, and identical state after
  the swap.
- `EVENT_STORE=eventstoredb` with the compose file up: run the whole M1–M3 demo against the real
  store, including the two-tab race for one seat.
- **Then kill the API and restart it.** The shows are still there, replayed from the log into fresh
  read models. This is the one gate the in-memory store could never pass, and the reason M4 exists.
