# M3 — the web seat map + the visible dev dashboard (SSE)

**Problem:** M1 and M2 built a correct, eventually-consistent CQRS system — but it's only visible
through `curl`. The whole thesis of open-ticket is that the hard parts (write contention, read/
write asymmetry, eventual consistency) become **watchable**. M3 delivers that: an **interactive
seat map** you can click to reserve, and a **dev dashboard** where commands arrive, events append,
and the projection catches up — **on screen, live**. This is the milestone the architecture was
built toward.

## Decisions (leivaa, 2026-07-26)

- **D3-01 — The seat map is interactive.** Clicking a seat reserves it (then confirm/release),
  driving the **real write API**; the map updates live. The demo that sells the project: open two
  browser tabs, race for the same seat, watch exactly one win and both converge — no double-sell,
  visibly.

- **D3-02 — Live updates over SSE, two feeds** (one-way server→browser, per the kickoff SSE
  decision). Each stream sends an initial snapshot on connect, then deltas; heartbeat comments keep
  it alive; the server cleans up the subscription on disconnect.
  - **Per-show seat map:** `GET /shows/:showId/seats/stream` (SSE) pushes the current
    `SeatMapView` (with `asOf`) whenever that show's projection advances. The buyer view
    subscribes here.
  - **Dashboard:** `GET /dev/stream` (SSE) pushes each newly-appended `$all` event (type + show +
    position) and the current **projection lag** (write head vs `asOf`). The dashboard subscribes
    here.

- **D3-03 — An in-process broadcaster bridges the projector to SSE.** When the projector applies
  events it notifies subscribers (per-show "this show changed" + a global "event appended / lag
  moved"); SSE handlers subscribe, forward, and unsubscribe on disconnect. No message bus — the
  broadcaster is a small typed event emitter, consistent with "no Kafka/RabbitMQ" (§ non-goals).

- **D3-04 — `apps/web`: Next.js (App Router) + Tailwind**, on **:5200**. It reuses
  `@open-ticket/contracts` read DTOs (via `transpilePackages`) so the wire shapes aren't
  re-declared. Server Components fetch the initial seat map from the API; Client Components
  subscribe to SSE and issue command `POST`s. The app never talks to the store — only the API.

- **D3-05 — Cross-origin is explicit CORS, not a wildcard.** The browser on `:5200` calls the API
  on `:5210` (SSE + command POSTs), so the API enables CORS **restricted to a configured
  `WEB_ORIGIN`** (env, default `http://localhost:5200`) — never `*`. Keeps the M1 security posture
  (public write endpoints stay origin-checked) while the two apps stay cleanly separate.

- **D3-06 — Polished, distinctive UI.** This is the portfolio's visible face: a considered dark
  theme, a seat grid with clear status colors and motion on state change, a real lag meter, and a
  streaming event feed. Liveness/correctness first, then aesthetics — but it should read as a
  product, not a homework grid. (Consult the dataviz guidance for the lag meter / feed.)

- **D3-07 — The dashboard is observational in M3.** It shows events + lag live. The **deliberate
  projector-throttle control** (drag lag up and watch reads go stale) and **published load
  numbers** are **M4** — M3 proves the visualization works; M4 stresses it.

## Architecture

```
  apps/web (:5200, Next.js)                         services/api (:5210)
  ┌───────────────────────────┐   HTTP POST cmds   ┌──────────────────────────────┐
  │ /shows/[id]  seat map      │ ─────────────────▶ │ command routes → use cases    │
  │   click → reserve/confirm  │                    │        │ append                │
  │   ◀── SSE seat updates ──── │ ◀── SSE ────────── │        ▼                      │
  │ /dev  dashboard            │   /…/seats/stream   │ event log ($all) → projector  │
  │   event feed + lag meter   │ ◀── SSE ────────── │        │ broadcaster           │
  │   ◀── SSE events + lag ──── │   /dev/stream       │        ▼ read models          │
  └───────────────────────────┘                    └──────────────────────────────┘
        reuses packages/contracts read DTOs        CORS: WEB_ORIGIN only
```

## SSE contract

Text `event:`/`data:` frames, `data` a JSON of a contracts-defined shape:

- `/shows/:showId/seats/stream`: `event: seatmap`, `data: SeatMapView` (initial + on each change).
  `404` if the show isn't projected; `event: ping` heartbeats.
- `/dev/stream`: `event: appended`, `data: { position, type, showId }` per new `$all` event; and
  `event: lag`, `data: { head, asOf, behind }` on change. Initial `event: lag` snapshot on
  connect.

## Sub-PR breakdown

1. **PR — API SSE + CORS.** The broadcaster (typed emitter fed by the projector), the two SSE
   endpoints (initial snapshot → deltas, heartbeat, disconnect cleanup), CORS restricted to
   `WEB_ORIGIN`. Tests: broadcaster unit (subscribe/emit/unsubscribe), SSE frame formatting,
   and a real-server integration reading a couple of frames over a socket (SSE doesn't stream
   through Fastify `inject`, so bind an ephemeral port). No web yet.
2. **PR — web scaffold + interactive seat map.** Next.js + Tailwind in `apps/web` (:5200),
   `transpilePackages` for contracts, typed API client; the `/shows/[id]` page — server-fetch the
   initial map, a client seat grid that live-updates from the seat SSE and lets you
   reserve/confirm/release. Focused tests on the SSE client hook + the seat-status reducer; CORS
   working end to end.
3. **PR — dev dashboard + design polish.** `/dev`: the streaming event feed + a projection-lag
   meter + a compact seat overview, live from `/dev/stream`; the polished visual pass across both
   pages (theme, seat motion, the lag meter). Wire `pnpm dev` (turbo) to run web + api together.

## Verify for real (gate two)

`pnpm dev` (api :5210 + web :5200). Confirm the SSE endpoints stream over `curl`. In the browser:
open `/shows/[id]` in two tabs, click the same seat in both → exactly one turns held, the other
sees it taken, live. Open `/dev`, drive some reservations, and watch events stream into the feed
and the lag meter move as the projection catches up. Capture screenshots for the README.

## Deferred (not M3)

The deliberate projector-throttle control + published load numbers + `stampede` integration (M4);
the real EventStoreDB adapter + persisted projections (M4); auth/real payments; multi-show lobby/
landing polish beyond what the demo needs.
