# M2 — projections + the read API

**Problem:** M1 gave us a correct write side, but the only way to see a show's state is to replay
its stream. The domain is read-heavy by nature — thousands watch a seat map, few buy — so reads
must come from **denormalized read models fed asynchronously from the event log**, not from
folding the write model per request. M2 builds that read side: an in-process **catch-up
subscription** driving a **seat-map** projection and an **availability summary**, served over
`GET` endpoints — and it makes the read side **eventually consistent on purpose**, so M3 can put
projection lag on screen.

## Decisions (leivaa, 2026-07-25)

- **D2-01 — Reads come from async catch-up projections, not on-demand folds.** A projector
  subscribes to the event log, replays history from position 0, then stays live, updating read
  models as events arrive. Reads hit the read model and may briefly lag the write side. This is
  the authentic CQRS/ES shape, mirrors an EventStoreDB catch-up subscription, and is the only
  design where projection lag is a real, observable quantity (M3's dashboard, M4's throttle demo).

- **D2-02 — The event log grows a global, positioned `$all` feed.** The in-memory store already
  holds per-stream events; M2 adds a **global append-ordered log** assigning each appended event a
  monotonic `GlobalPosition` (0-based). A read-side port exposes it: `readAll(from) → {events,
head}` (catch-up pull) plus an `onCommitted` notification (live wake-up). This mirrors
  EventStoreDB's `$all` + subscriptions, so the real client stays a drop-in. The write-side
  `EventStore` port is unchanged; the read port is separate (a store may implement both).

- **D2-03 — A catch-up subscription primitive in the application layer.** `subscribe(from,
handler)` replays `readAll` from `from`, applies each event, tracks its position, then processes
  live commits via the notification — serialized (never processes two batches concurrently),
  resumable, and driven by an injected scheduler so tests are deterministic (no real timers). Its
  position is public: **lag = log head − subscription position**.

- **D2-04 — Read models are time-aware for hold liveness (mirrors lazy expiry).** M1's domain
  frees an expired hold lazily — no `HoldExpired` event until the M4 sweeper. So the seat-map
  projection stores each held seat **with its `expiresAt`**, and the query layer resolves
  effective status against an injected `Clock`: a hold past `expiresAt` reads as **available**.
  This keeps reads consistent with what a `ReserveSeats` would actually allow, without inventing a
  sweeper in M2. Sold is terminal; released removes the hold.

- **D2-05 — Reads are eventually consistent and say so (`asOf`).** Every read response carries
  `asOf`: the global position the projection reflects. A show whose `ShowScheduled` the projector
  hasn't applied yet reads **404** (honestly "not visible yet", not "doesn't exist"). A client
  comparing the `asOf` it sees to a write's returned revision can tell whether its write is
  visible — the seam M3's dashboard uses to render lag. No read-your-writes wait in M2 (deferred).

- **D2-06 — Read models are in-memory and rebuildable.** Consistent with the in-memory event
  store; a projection is a disposable view rebuilt by replaying from position 0. Persistence
  arrives with the real EventStoreDB adapter (M4). A projector restart replays the whole log.

## Read API

- `GET /shows/:showId/seats` → `200 { showId, asOf, seats: [{ seatId, status }] }` where `status`
  ∈ `available | held | sold` (held resolved against the clock per D2-04). `404` if not yet
  projected.
- `GET /shows/:showId` → `200 { showId, asOf, total, available, held, sold }` — the availability
  summary (counts). `404` if not yet projected.

Both are pure reads off the projection — no folding, O(1)-ish in the show's seat count.

## Sub-PR breakdown

1. **PR — the positioned `$all` log + catch-up subscription.** Extend the in-memory store with a
   global positioned log + `readAll(from)` + `onCommitted`; a read-side `EventLog` port; the
   `subscribe(from, handler)` primitive (catch-up → live, serialized, injected scheduler). Unit
   tests: replay from a position, live delivery after catch-up, position/lag tracking, no
   concurrent batch processing.
2. **PR — the seat-map + availability projections and the projector.** Pure projection reducers
   (event → read-model update) for `SeatMap` and `AvailabilitySummary`; the time-aware query layer
   (D2-04); a `Projector` wiring the reducers to a subscription, rebuildable from 0, position
   tracked. Tests: project a crafted stream → correct map/summary; a lazy-expired hold reads
   available; released frees, sold is terminal; rebuild == incremental.
3. **PR — the read API.** `GET` endpoints wired to the read models, `asOf` exposed, 404-before-
   projected behavior, no internal leak. Fastify `inject` integration tests, and an end-to-end
   test: `POST` a reservation, let the projector catch up, `GET` the seat map and see the seat
   `held` with `asOf` advanced.

## Verify for real (gate two)

Run the server: schedule a show, `GET` the seat map (all `available`), `POST` a reservation,
`GET` again and watch the seat flip to `held` with `asOf` advanced; confirm it and watch it flip
to `sold`. Observe the projection catching up (asOf trailing then matching the write revision).

## Deferred (not M2)

SSE streaming of read-model changes + the web dashboard (M3); a background expiry sweeper emitting
`HoldExpired` (M4); the real EventStoreDB `$all` subscription + persisted projections + load
numbers (M4); read-your-writes / wait-for-projection; multi-projector scaling.
